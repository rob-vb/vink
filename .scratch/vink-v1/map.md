# Vink v1 — map

Label: wayfinder:map

## Destination

A build-ready spec at `.scratch/vink-v1/spec.md` (plus ADRs for hard calls) for v1: a user creates a Form, uploads a PDF (incl. handwritten), a pipeline fills every Field with a confidence-scored Field Value, low-confidence values are Needs Review, and after Approval (manual, or automatic via the Form's Auto-Send) the Payload is POSTed as JSON to an Integration. When no tickets remain, write the spec with `/to-spec`.

## Notes

- Domain: multi-tenant SaaS for document data extraction. Vocabulary in `CONTEXT.md` — use its terms (Form, Field, Document, Field Value, Confidence, Review Threshold, Needs Review, Auto-Send, Approval, Payload, Integration).
- We talk Dutch; the app, code and all terms are English.
- Grilling tickets: call the Skill tool for `grilling` and `domain-modeling`. Research tickets: `research`. Anything involving Jev/TypeSafe: also consult the `typesafe:typesafe-ai` skill.
- Cost-efficiency is a first-class criterion for the extraction pipeline; handwriting support is highly desired.
- Settled while charting: intake is upload-only; Form is chosen by the user at upload; Payload is keyed by the Form's own Fields (no mapping to target fields); Auto-Send is set per Form (refined in Confidence semantics and auto-send rules); stack leans TypeScript.
- Testing approach: extraction is first tested locally with a Claude Code agent (Sonnet or Opus) reading the PDFs, with no API integration. The production pipeline moves to an API later, probably Gemini (Vertex EU).
- Reference use case: tire reports (tyre swaps etc.) — the user built a similar tool before.

## Decisions so far

<!-- one line per closed ticket: [title](issues/NN-slug.md) — gist -->

- [PDF extraction options and cost](issues/01-pdf-extraction-options.md) — Classic OCR can't read Dutch handwriting, so vision models or Mistral OCR 4 it is. Cost is negligible either way; handwriting accuracy and confidence decide. Candidates: Gemini Flash, Claude Sonnet, Mistral OCR plus a text model, all routed through the EU.
- [TypeSafe/Jev capabilities and fit](issues/02-typesafe-jev-capabilities.md) — Jev is text-only and never writes values. Use it for per-Field checks, confidence, escalation and Form selection, not for extraction or handwriting. It is cheap, but in early access and US-hosted.
- [Test document set with ground truth](issues/03-test-document-set.md) — Starter set of 5 PDFs in `fixtures/`: 4 tyre-service (3 suppliers, 2 with handwriting) and 1 invoice. The agent proposed the Forms. Ground truth comes from the user correcting the first benchmark output. Most PDFs bundle several Documents, and Forms need repeating groups.
- [Field model](issues/04-field-model.md) — There are 6 Field types, and List Fields (repeating groups) go one level deep. Each Field has a label, a key, a description and a required flag. v1 validates by type only. Missing required values and values of the wrong type become Needs Review. Every cell has its own confidence, and each List Field also gets a completeness confidence. The read text is kept for review. Every key is always in the Payload (`null` for no value, `[]` for an empty list). A Document is tied to its Form Version.
- [Delivering a Payload to an Integration](issues/05-integration-delivery.md) — An Integration belongs to the Organisation and can be attached to several Forms, and one Approval sends to all of them. Auth uses static headers plus an HMAC signature. The Payload is wrapped in an envelope with metadata. Retries back off for about 8 hours, with at-least-once delivery. Each Document has one Delivery per Integration, and a failed Delivery can be re-sent by hand. Test-send uses dummy data. In v1, sent means done.
- [Stack, hosting and tenancy](issues/06-stack-hosting-tenancy.md) — Next.js with shadcn/ui runs on the Hetzner VPS. Convex Cloud EU is the database, backend and queue, and PDFs go in Cloudflare R2 (EU). Auth is Better Auth. Users reach Organisations through Memberships with the role Admin or Member, and Organisations are isolated by a function wrapper. PDFs are kept for 30 days after Delivery by default. See [ADR 0001](../../docs/adr/0001-convex-cloud-eu-backend.md).
- [Benchmark extraction pipelines](issues/07-pipeline-benchmark.md) — The local run with Claude reading the PDFs visually read almost every Field correctly, handwriting included. Opus beat Sonnet. The weak spot is List completeness in bundles: two tyre changes were merged into one entry at 0.8+ confidence. Self-reported confidence roughly ranks right above wrong, but it is not calibrated. Brand names are written out in full. Cost, latency and Jev are deferred to the API pipeline benchmark.
- [Extraction pipeline design](issues/08-extraction-pipeline.md) — The whole PDF, with its text layer, goes to one vision model on Vertex EU, which returns every Field Value with its source page(s). The model is chosen by the API pipeline benchmark. List completeness is checked in code against a per-page inventory. Jev only verifies each value (fit, plausibility, support by the source text); it is a US subprocessor that an Admin can switch off. Without a Jev result there is no Auto-Send. Uploads are limited to 20 pages, and a PDF is never split. See [ADR 0002](../../docs/adr/0002-vision-extraction-with-jev-verification.md), partly superseded by API pipeline benchmark.
- [Confidence semantics and auto-send rules](issues/09-confidence-and-auto-send.md) — Confidence ranks values; it is not a probability. It is the lowest of the self-report and the Jev checks, and code checks flag values directly. Each Form has a Review Threshold (default 0.8) and an Auto-Send switch (default off) that approves only when nothing is Needs Review and Jev verified the Document. Raw signals are kept for later calibration.
- [Review screen prototype](issues/10-review-screen.md) — Side by side: the PDF on the left, the editable Fields on the right, with the read text, a confidence bar plus number, and why each value is Needs Review. Selecting a row jumps to its source page; highlighting the region is optional. Bundles are fixed by adding an entry by hand. Approval is blocked until nothing is Needs Review.
- [API pipeline benchmark](issues/11-api-pipeline-benchmark.md) — Run locally with Claude Code and real Jev calls; the pipeline changes to the user's design. A vision model writes a Form-independent Reading (clean JSON), Jev matches it to the Form's Fields, a small model fills the values, and Jev verifies (80/84, Lists 4/4). The ground truth of tire-service-002 was one tyre change, not two. pdf-inspector supplies the text layer. See [ADR 0003](../../docs/adr/0003-reading-then-jev-matching.md).
- [Firecrawl as a PDF extraction route](issues/13-firecrawl-pdf-extraction.md) — Hosted Firecrawl is ruled out. It costs more than Gemini Flash, stores data in the US, doesn't read Dutch handwriting, and gives no confidence per field. Its local open-source library pdf-inspector could replace the pdf.js triage: it provides per-page markdown and, on typed pages, text positions for highlighting and for Jev's source check. Whether it runs in Convex needs a test deploy.
- [Wrong Form or unusable Document](issues/12-wrong-form-or-unusable-document.md) — Before Approval a user can use Change Form, which re-runs Match and Fill on the stored Reading against the new Form's current Form Version and drops the old corrections, or Reject. Rejected is a visible end state that is never sent; its data is deleted 30 days later, and it can be reopened until then. Only an Admin can Delete, and only a Rejected Document. A "Does not fit this Form" flag, set in code from the Match result, blocks Auto-Send. Any user action rules out Auto-Send.
- [Form proposal from a sample Document](issues/14-form-proposal-agent.md) — In v1, as the normal way to start a Form. An Admin uploads one sample PDF, the vision model sees its Reading and pages and proposes Fields: printed labels, English keys, descriptions with synonyms, and no required flags. Everything is listed, and the useful Fields are pre-ticked. The Admin edits the Form Proposal and saves a Form Version, and the sample can become the first Document. A second sample adds only the Fields that Match can't place. A bundle gets one Form. No separate benchmark.
- [Extraction without Jev](issues/15-extraction-without-jev.md) — Jev is required in v1. The Admin switch is dropped, and there is no fallback matcher and no fallback benchmark. If Jev still fails after the retries, the Document is Extraction Failed and a manual retry resumes from the stored Reading. If only Verify fails, the Extraction succeeds without Auto-Send. TypeSafe now receives the whole Reading, so its zero-retention quote and the transfer impact assessment block launch.
- [Firecrawl /parse as the Read step, then Jev](issues/16-firecrawl-parse-then-jev.md) — We're pursuing the user's Firecrawl route so the pipeline needs no vision model. Two variants are benchmarked: /parse markdown straight to Jev, and /parse markdown turned into the Reading by a text model. Fill stays. The route replaces ADR 0003's Read step only if it reaches 80/84 values, Lists 4/4 and correct handwriting. Firecrawl becomes a second US subprocessor; the DPA with SCCs (paid plan, no Enterprise) is arranged later, before launch.
- [Firecrawl route benchmark](issues/17-firecrawl-route-benchmark.md) — Both variants miss the bar: 53/84 and 57/84 values, Lists 1/4 and 2/4. GLM-OCR loses the Dutch handwriting (misread serials, dropped page) and gives no OCR confidence. ADR 0003 stands, and Firecrawl drops out as a subprocessor.
- [Read thinking level](issues/39-read-thinking-level.md) — Read stays at thinking `HIGH`. `MEDIUM` met the bar (80–81/84) at half the cost and about 7× faster on 20 pages, but it misread a handwritten mileage digit without flagging it. `READER_THINKING` overrides the level.

## Out of scope

- Developer agent that builds Integrations from API docs — later version.
- Pre-built Integrations for specific systems (Exact, AFAS, …) — later version.
- Mapping Form Fields onto an external system's target fields — v1 sends the Form's own JSON.
- Intake via inbound email, mailbox connection or API — v1 is upload-only.
- OAuth2 auth for Integrations, email notifications for failed Deliveries, a PDF link in the Payload, and automatic re-send after a correction — deferred to a later version while resolving [Delivering a Payload to an Integration](issues/05-integration-delivery.md).
- Splitting one PDF into several Documents, and PDFs over 20 pages. Ruled out for v1 in [Extraction pipeline design](issues/08-extraction-pipeline.md): one PDF is one Document.
- Running the pipeline on Vertex EU: the real reader's cost and latency, Gemini vs Claude as the reader, EU availability, pinned versions, and pdf-inspector in a Convex Node action. The user decided in [API pipeline benchmark](issues/11-api-pipeline-benchmark.md) that this happens once the app is built; ADR 0003 keeps the models as configuration.
- Re-extracting a single page to propose a missing List entry. Ruled out for v1 in [Review screen prototype](issues/10-review-screen.md): users add the entry by hand.
- Automatic Document-type detection (choosing the Form for the user): v1 has the user pick the Form at upload. The "Does not fit this Form" flag from [Wrong Form or unusable Document](issues/12-wrong-form-or-unusable-document.md) is the groundwork for a later version.
- Learning from user corrections to improve future extractions: later version. Stored raw signals and corrections are kept, per [Confidence semantics and auto-send rules](issues/09-confidence-and-auto-send.md).
- Growing the test set to 30–50 Documents for confidence calibration: this is post-build work, since it needs the real pipeline running on Vertex EU. v1 ships with the Review Threshold default of 0.8.
- Subprocessor paperwork (TypeSafe zero-retention quote, DPA/SCC, TIA): a pre-launch to-do, not part of the spec.
- Billing and pricing (per page, and whether Form Proposal samples count): outside the v1 spec. Pricing waits for real Vertex costs.
